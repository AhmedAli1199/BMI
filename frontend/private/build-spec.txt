1. How to read this document
This is the complete build specification for the MVP “Sales & Data Brain” (Option 2) — the five workstreams below and every automation inside them. Enough detail for a developer to scope and quote each one. No sales narrative.
* Platform: everything is built and orchestrated in n8n, self-hosted, calling the Act! Web API over HTTPS. No cloud CRM migration.
* Guardrail (everywhere a message is produced): the system drafts, the salesperson sends. No client-facing auto-send. A mandatory human approval step sits in every drafting workflow.
* To quote: each automation carries an indicative build-day estimate. Quote = (total build-days × your day rate) + monthly running costs (Section 5). Estimates are pre-scoping; several move on the answers in Section 6.
* Each automation block contains: Goal · Trigger · Inputs/sources · Systems & APIs · Build (n8n flow) · AI/model work · Data model/writes · Edge cases & failure modes · Config/parameters · Human-in-the-loop · Acceptance test · Depends on · Effort drivers.

4. The automations, in detail
Stage 1 — The Hub & the Clean Foundation
CS-001 — Bounce Classification & Processing
Medium · Est. 3–5 days
Goal. Collect bounce replies from each mailing, classify every one, and action hard bounces in Act! automatically while routing recoverable signals downstream. Trigger. Scheduled inbox-watch (n8n Cron, every 15–30 min) polling the sending mailbox(es) after any title/salesperson mailing; new messages matching bounce heuristics enter the flow. Inputs / sources. Raw bounce/DSN emails from the sending inbox (O365/Exchange — confirm platform): SMTP status headers, X-Failed-Recipients, MTA body text, original-recipient address, subject. Systems & APIs. Email integration (inbox-watch); LLM API (classification); Act! Premium Web API (Contacts lookup + write) — confirm Premium, not Pro; Teams notification; human-review queue. Build (n8n flow). 1) Schedule trigger → O365 node getAll messages (filter: unread, DSN/subject patterns). 2) Function node parses SMTP code + failed-recipient from headers; regex pre-filter (5xx vs 4xx). 3) Ambiguous/text-only bounces → LLM classify node. 4) Switch on class: hard → Act! GET /contacts?filter=email eq then PATCH contact (unsubscribe flag) + POST /histories; soft → append to soft-bounce datastore, increment counter; OOO/referral → HTTP call to CS-002 sub-workflow; auto-reply-noise → mark read. 5) Aggregate per-mailing → summary table → Teams post + review queue for unclear. AI / model work. Input: bounce body + headers + original recipient. Returns {recipient_email, class: hard|soft|ooo|autoreply_referral|unknown, smtp_code, reason_text, names_alternate: bool, confidence}. Data model / writes. New datastore bounce_events (recipient, mailing_id, class, smtp_code, count, first_seen, last_seen). Act!: Contact unsubscribe field set; History record stamped source=CS-001 bounce, date. No hard delete — flag + retain. Edge cases & failure modes. Non-English MTA text; bounces where recipient differs from list address (relay/alias); challenge-response auto-replies mis-read as referral; catch-all domains that never hard-bounce; multiple bounces per contact across three titles; Act! email match failing on formatting. Config / parameters. Poll cadence; SMTP-code→class map; soft-bounce escalation threshold (e.g. 3 fails/30 days); confidence threshold for auto-action; per-title inbox list. Human-in-the-loop. unknown/low-confidence rows land in the review queue; specialist confirms class, which then triggers the write. Acceptance test. Feed a 200-bounce fixture folder: ≥95% classified correctly vs hand-labelled key; every hard bounce flagged in Act! with a History stamp; OOO items appear in CS-002 input; summary counts reconcile. Depends on. Email integration, Act! Web API, LLM, review queue. Feeds CS-002 and CS-003. Effort drivers. Up: multi-inbox/multi-title auth, messy MTA formats, Act! email-match reliability. Down: single inbox, clean DSN headers, generous confidence threshold.
CS-002 — Out-of-Office Replacement Mining
Medium · Est. 3–5 days
Goal. Read each OOO/auto-reply for a named alternate, successor or return date, verify against Act!, and write the replacement with a compliance note. Trigger. CS-001 hands off any reply classed ooo or autoreply_referral. Inputs / sources. The OOO email body (names, alternate emails/phones, return dates, “in my absence contact…”), original contact record, three-title Act! database. Systems & APIs. LLM API (extraction); Act! Web API (Contacts search/create/update, Notes/History); enrichment provider (optional email-pattern verify); review queue. Build (n8n flow). 1) Sub-workflow trigger receives {email, message_id, body}. 2) LLM extraction node pulls alternate/successor/return-date/general-address. 3) Branch: named alternate → Act! GET /contacts fuzzy match on name+company to avoid dupes → if exists, link; if not, POST /contacts under same Company. 4) PATCH original contact + POST /notes compliance note (source + date). 5) Departure-only (confirms gone, no alternate) → HTTP to CS-003. 6) Ambiguous → review queue with original reply attached. AI / model work. Input: OOO body + originating contact. Returns {alternate_name, alternate_email, alternate_phone, is_successor: bool, return_date, general_address, departure_confirmed: bool, confidence}. Data model / writes. Act!: new/linked Contact; Note stamped source=OOO reply <message_id>, date=<recv>; original contact updated (status/replacement link). No deletion. Edge cases & failure modes. Temporary absence (return date) mistaken for permanent replacement — must NOT replace; PA/reception given as generic alternate; alternate already in DB under variant spelling; multiple names in one reply; alternate email domain mismatch (external PA). Config / parameters. Return-date grace window (skip replacement if returning ≤N days); fuzzy-match threshold; confidence auto-write threshold; compliance-note template. Human-in-the-loop. Ambiguous/low-confidence and any successor-vs-temporary uncertainty queue for the specialist; original reply always attached. Acceptance test. Fixture set of OOO replies: named alternates written to Act! with correct Company link and no duplicate; temporary-absence replies produce no replacement; every write carries a source+date Note. Depends on. CS-001 (input), Act! Web API, LLM, review queue. Feeds CS-003. Effort drivers. Up: dedupe fuzzy-matching quality, temporary-vs-permanent disambiguation. Down: high-confidence-only auto-write, rest to queue.
CS-003 — Departure Detection & Successor Finding
High · Est. 6–9 days
Goal. Detect a contact’s departure from any signal, find and verify the same-role successor, write them across every company record, and fall back to a verified general address where no successor is confirmed. Trigger. Three signal sources: no-longer-here hard bounces (CS-001), OOO-without-alternate (CS-002), and the people-move monitor (marketing-system alerts / enrichment). Inputs / sources. Departure signal payload; the leaver’s contact + every sibling record under the same Company across three titles/lists; external successor research (enrichment/LinkedIn — confirm method, GDPR note); company general contact page. Systems & APIs. LLM API (research synthesis + verification); enrichment provider (LinkedIn→email, people-move); Act! Web API (Company → related Contacts fan-out, multi-record update, Notes); web fetch; review queue; Teams. Build (n8n flow). 1) Trigger merge node normalises the three signal shapes → {company, leaver_contact_id, signal_type}. 2) Act! GET /companies/{id}/contacts (or Group query) to enumerate every record the person holds — one company can hold 6+. 3) Enrichment/web research node → candidate successor in same role/title. 4) LLM verification node scores candidate against role+company; confidence gate. 5) If confirmed → loop PATCH each sibling record with new person + POST /notes (source+date); if not → resolve verified general company address, substitute on records so circulation continues. 6) Unresolved → review queue with research bundle; Teams alert. AI / model work. Input: leaver details + enrichment results + company page text. Returns {successor_name, successor_title, successor_email, successor_phone, role_match: bool, evidence_urls[], confidence} and, on failure, {general_address, address_source, confidence}. Data model / writes. Act!: bulk Contact updates across all sibling records; retired-leaver flag (retain history); Notes stamped per record with source+date. Datastore departures (company, leaver, signal_type, resolution: successor|general|queued). Edge cases & failure modes. Wrong-person successor (common name); role split across two people; company restructure/closure; enrichment stale or GDPR-restricted; only some of the 6 records found (matching gaps); general address unverifiable; re-processing the same departure from two signals (idempotency). Config / parameters. Signal-source list; confidence gate for auto-write vs queue; general-address fallback rule; enrichment provider + rate limits; dedupe/idempotency key (company+leaver). Human-in-the-loop. All unconfirmed successors and any multi-record ambiguity queue with research attached; specialist confirms before bulk write. Acceptance test. Given a known departure, flow enumerates ALL sibling records, proposes the correct successor with evidence URLs, and on confirm updates every record with a stamped Note; where no successor exists, a verified general address is substituted on all records. Depends on. CS-001, CS-002, enrichment/people-move monitor, Act! Web API, LLM. Effort drivers. Up: three heterogeneous signal sources, multi-record fan-out reliability, successor-verification accuracy, enrichment integration + compliance. Down: single signal source first, queue-heavy (less auto-write).
CS-004 — Duplicate & Moved-Person Record Merging
High · Est. 6–9 days
Goal. Detect duplicate and similar-name records across reader lists and the ~40k prospects DB, confirm moved-person cases, merge old into new with history preserved, and run a rolling retirement pass. Trigger. Event: new registration/re-subscription resembling an existing record. Scheduled: rolling dedupe pass over the prospects database in reviewable batches. Inputs / sources. Incoming registration/re-sub payload; existing Act! Contacts (reader lists + prospects DB); LinkedIn check (confirm method); re-subscription completion status (identify silent failures). Systems & APIs. Act! Web API (search, merge/retire, Notes) — or SQL Server Express read fallback for bulk scan; LLM API (match adjudication); enrichment/LinkedIn (identity confirm); review queue; Teams. Build (n8n flow). 1a) Event path: on new reg → Act! search exact email, then fuzzy name+company → candidate set. 1b) Batch path: Schedule node pulls N records → blocking key (surname/email-domain) → pairwise similarity. 2) LLM adjudication on candidates (same person, new company?). 3) LinkedIn/enrichment check for moved-person confirmation. 4) Confirmed move → merge old→new (company updated, history preserved, old details retired) + POST /notes source+date. 5) Silent re-sub failures diagnosed (blocked at subscriber end) → resolve/flag. 6) Batch → dead/stale/dupe candidates listed for retirement; uncertain → queue. AI / model work. Input: record pair(s) + enrichment. Returns {same_person: bool, move_detected: bool, old_id, new_id, changed_fields[], recommendation: merge|retire|keep|review, confidence}. Data model / writes. Act!: merge (survivor = new record) with history carried; retired records flagged with reason; Notes stamped source+date. Datastore dedupe_runs (batch_id, reviewed, merged, retired, queued). Edge cases & failure modes. False-merge of genuinely different people (namesakes) — irreversible risk; partial-match families (father/son, same name); merge API limitations in Act! (may need field-copy + retire pattern); 40k-record scan performance (favour SQL read); GDPR on retention vs deletion; re-sub silently blocked at ESP end. Config / parameters. Similarity thresholds (auto-merge vs review vs ignore); blocking keys; batch size + schedule; “9-in-10 same person” heuristic weighting; retirement staleness rule (last-activity age). Human-in-the-loop. Uncertain matches never auto-merge — queue for specialist; rolling-pass retirements reviewed in batches before action. Acceptance test. Seeded dupes/moves: confirmed moves merge with survivor=new and history intact + stamped Note; namesake trap pairs are NOT merged (routed to review); batch pass produces a reviewable retirement list, nothing deleted silently. Depends on. Act! Web API (+SQL fallback), LLM, enrichment/LinkedIn, review queue. Effort drivers. Up: Act! merge mechanics, 40k-scale scan, false-merge safety tuning, GDPR. Down: review-first (no auto-merge), SQL read access granted.
CS-005 — Returned Copy Processing
Low · Est. 1–2 days
Goal. Read each returned print-copy label, match it to its Act! record, and correct the address or retire the record with a reason. Trigger. A batch of undeliverable printed copies returned by the post office after an issue mailing; operator photographs/scans the labels and uploads. Inputs / sources. Label images (name, company, address, possibly a customer/mailing ref); Act! Contacts; company-move/closure evidence (web/enrichment, optional). Systems & APIs. OCR/vision (label read) — confirm intake: upload form vs email; LLM API (parse + address adjudication); Act! Web API (Contacts match, address update, History); review queue. Build (n8n flow). 1) Form/email trigger receives label images as a batch. 2) OCR/vision node → text per label. 3) LLM parse → structured address + ref. 4) Act! GET /contacts match on ref → fallback name+company+postcode. 5) Branch: company moved → PATCH address + POST /histories; company closed → retire flag + reason History; unmatched → review queue. 6) Batch summary per title → Teams/queue. AI / model work. Input: OCR label text. Returns {contact_ref, name, company, address, match_hint, outcome: correct_address|retire_closed|unmatched, new_address, reason, confidence}. Data model / writes. Act!: address fields updated OR retired flag + reason; History stamped source=returned copy, date. Datastore returns_batches (batch_id, returned, corrected, retired). Edge cases & failure modes. Poor OCR on skewed/marked labels; multiple contacts at one returned address; no ref on label (name/company match only); temporary vs permanent move; retire-vs-correct ambiguity. Config / parameters. Match key priority; confidence threshold; intake channel; retire-reason taxonomy (moved/closed/unknown). Human-in-the-loop. Unmatched and low-confidence labels queue for a quick review; physical pile stays with the team. Acceptance test. Upload a labelled returns batch: each label OCR’d and matched, moved-company addresses corrected and closed ones retired with reason + History; unmatched routed to queue; summary counts reconcile. Depends on. OCR/vision, LLM, Act! Web API, review queue. Effort drivers. Up: OCR quality on physical labels, no-ref matching. Down: refs present, clean scans, correct-only (retirement to review).
SALES-001 — Business Card Reading & Extraction
Low · Est. 2–3 days
Goal. Turn photographed trade-show business cards (several per photo) into structured contact records, flagging anything unreadable. Trigger. Team member uploads card photos via a simple form or by email after a show. Inputs / sources. Card photos (varied layouts/typefaces, multiple cards per image); the show name + date supplied at upload. Systems & APIs. Intake form/email (confirm channel); OCR/vision model (card detection + read); LLM API (field structuring); passes batch to SALES-002. Build (n8n flow). 1) Form/email trigger captures images + show_name, show_date. 2) Vision node detects and crops each card region in a multi-card photo. 3) Per-card OCR/vision extraction. 4) LLM structuring node normalises fields. 5) Confidence check → low-confidence cards flagged. 6) Assemble structured batch with show/date stamped on every contact → HTTP to SALES-002. AI / model work. Input: card image(s). Returns per card {name, company, job_title, email, phone, address, confidence, needs_review: bool}; multi-card images return an array. Data model / writes. No Act! write here — produces staging batch card_extractions (temp store / passes to SALES-002) with source_show + source_date on each row. Edge cases & failure modes. Multiple cards overlapping in one photo; double-sided cards (logo/blank reverse); non-Latin scripts; QR-only “digital” cards; handwriting on card; glare/rotation; multiple emails/phones per card. Config / parameters. Intake channel; confidence threshold for needs_review; expected field set; max cards per image. Human-in-the-loop. needs_review cards flagged for a quick human correction before dedupe (SALES-002); nothing guessed. Acceptance test. Upload photos incl. multi-card shots: each card separated and extracted with correct fields at ≥ target accuracy; unreadable cards flagged not guessed; every row carries show + date. Depends on. OCR/vision, LLM, intake channel. Feeds SALES-002. Effort drivers. Up: multi-card separation reliability, double-sided/QR handling. Down: single-card photos, generous review flagging.
SALES-002 — Card Contact Dedupe & Group Assignment
Low · Est. 1–2 days
Goal. Check each read card contact against Act!, suggest CRM groups for new ones, surface changed details on existing ones, and write the batch on one confirmation. Trigger. A batch of read card contacts arrives from SALES-001. Inputs / sources. Structured card batch (name, company, email, title, phone, address, show, date); existing Act! Contacts + Group structure (company type, role, territory). Systems & APIs. Act! Web API (Contacts search, Groups read/assign, create/update, Notes); LLM API (group suggestion + change detection); human-review UI (confirm list). Build (n8n flow). 1) Trigger receives batch. 2) Per contact: Act! GET /contacts match on email, then name+company (email-pattern heuristic). 3) Existing → diff incoming vs stored → highlight changed fields. 4) New → LLM suggests Groups from existing Act! group taxonomy. 5) Build review list (additions+suggested groups; updates+changes) → review UI. 6) On confirm: POST /contacts (new) + POST /groups/{id}/contacts; PATCH (updates); stamp source_show+date Note on each. 7) Summary of added/updated/skipped → Teams. AI / model work. Input: contact + Act! group taxonomy. Returns {match_status: new|existing, matched_id, changed_fields[], suggested_groups[], confidence}. Data model / writes. Act!: new Contacts, Group memberships, updated fields; Note/field stamped source_show + date on every record. Datastore card_batches (batch_id, added, updated, skipped). Edge cases & failure modes. Same person, different company (not a dupe — new record); company-name variants blocking match; generic info@ emails defeating email-pattern match; unknown group (no fit in taxonomy); two new cards that are dupes of each other within one batch. Config / parameters. Match key priority + threshold; group-taxonomy source; email-pattern rules; auto-write vs confirm gate. Human-in-the-loop. One review-list confirmation writes the batch; specialist adjusts suggested groups and resolves flagged existing-contact changes before commit. Acceptance test. Feed a batch with known dupes + new contacts: existing recognised (not duplicated), new contacts get sensible group suggestions, one confirm writes all with show+date stamps, summary reconciles added/updated/skipped. Depends on. SALES-001 (input), Act! Web API (Contacts + Groups), LLM, review UI. Effort drivers. Up: group-suggestion quality against real taxonomy, company-variant matching. Down: small/clean taxonomy, confirm-everything (no auto-write).
Stage 1 subtotal: 22–35 days.
Stage 2 — The Living Memory + AI Chat
SALES-008 — Call Note Capture to the CRM
Medium · Est. 4–6 days
Goal. Turn every finished Teams/Zoom sales call into a structured, tagged Act! Note against the right contact, with zero manual typing. Trigger. Call-ended / transcript-ready event from the meeting platform (Graph callRecord webhook for Teams, or Zoom recording.transcript_completed webhook). Fallback: n8n Schedule node polling the transcription store every 15 min. Inputs / sources. VTT/JSON transcript, meeting metadata (organiser UPN, participant emails/domains, start/end, title). Systems & APIs. Teams/Zoom transcription (licensing to confirm), LLM API (provider + GDPR/data-residency to confirm), Act! Web API — Contacts, Companies, Notes, Groups; SQL Express read fallback; Teams notification for the digest. Build (n8n flow). 1) Webhook Trigger receives call-ended event. 2) HTTP node fetches transcript + metadata. 3) Function node normalises speaker turns, strips fillers, chunks if >context window. 4) Contact/company match: query Act! Contacts by participant email; if no email hit, match company by email domain, then fuzzy-match attendee name within that company (SQL fallback for speed). 5) LLM extraction node → structured JSON. 6) Switch on match_confidence: high → write; low → human-review queue. 7) Act! POST Note (bearer token), linked to contact GUID. 8) Tag budget/timing signals onto contact via Group membership or note keywords. 9) Append row to per-rep digest store. 10) Error branch → review queue + Teams alert. AI / model work. Model reads transcript, outputs: {contact_guess, company_guess, interest_summary, products_discussed[], rates_mentioned[], budget_signal{amount,window}, timing_signal, objections[], personal_notes[], match_confidence}. Prompt pins rates/dates verbatim; temperature low. Data model / writes. One Act! Note per call, body = formatted summary, stamped date · source=“Teams/Zoom call” · salesperson. Budget + timing signals additionally tagged (Group or keyword field) so the follow-up engine can query them. No contact fields overwritten. Edge cases & failure modes. Multi-party call → attribute to primary external contact; log others. No transcript / silent call → skip, log. Ambiguous contact (shared domain, name absent) → review queue, never guess-write. Act! token expiry / 401 → refresh + retry with backoff. Duplicate webhook → idempotency key on call ID. Config / parameters. Match-confidence threshold; digest send time; min call duration; rate/date extraction strictness; retry/backoff. Human-in-the-loop. Daily per-rep digest lists captured notes with one-click correct/reject; low-confidence matches held until confirmed. Acceptance test. Seed a recorded call naming a known Act! contact, two products, a rate and a “budget in November” line → within 15 min a Note appears on that contact, stamped correctly, with the rate verbatim and a budget/timing tag queryable by the follow-up engine. Depends on. Transcription licensing + webhook access; Act! Premium Web API (not Pro); LLM provider + residency sign-off. Effort drivers. Contact-matching reliability across 10k contacts; transcript chunking; tag schema shared with the follow-up engine; digest UI.
SALES-009 — Proposal Logging to the CRM
Medium · Est. 3–5 days
Goal. Detect every outbound proposal and log exactly what was quoted (products, prices, terms) against the client in Act!, creating the contact if new. Trigger. Outbound send matching an agreed convention (subject/body begins “proposal”). O365/Exchange (platform to confirm): Graph subscription on Sent Items, or n8n inbox-watch on the sent folder. Inputs / sources. Sent email body + attachments (PDF/DOCX quote), recipient address, sender (rep) identity. Systems & APIs. Email integration (O365/Exchange TBC), OCR/vision (scanned/PDF quotes), LLM API, Act! Web API — Contacts, Companies, Groups, Notes, Activities (follow-up). Build (n8n flow). 1) Sent-mail trigger → filter on “proposal” convention. 2) Extract body text; if attachment present, route PDF/DOCX through OCR/vision to text. 3) LLM parses line items. 4) Match recipient in Act! by email; if absent → create contact (name/company/email from signature) with suggested Groups. 5) POST structured Note recording the quote. 6) Create Act! Activity (follow-up task) dated per config. 7) Unreadable attachment or ambiguous parse → human-review queue, not silent skip. AI / model work. Input: email + extracted attachment text. Output: {client_email, company, line_items[{product, qty, unit_price, terms}], total, currency, valid_until, suggested_groups[], parse_confidence}. Prices verbatim; flag any figure it could not read. Data model / writes. Act! Note (quote detail) stamped date · salesperson · source=“Proposal email”; new Contact created with Group membership + source stamp when unmatched; Act! Activity created as the follow-up trigger. Edge cases & failure modes. Attachment unreadable/encrypted → review queue. Proposal to existing multi-contact company → attach to the addressed contact. Convention false-positives → confidence gate + rep confirm on new-contact creates. Revised/re-sent proposal → append new Note, don’t overwrite. Multi-currency / discount lines → capture as-is. Config / parameters. Detection convention (prefix/subject regex); follow-up offset (days); OCR confidence floor; auto-create vs confirm-first for new contacts. Human-in-the-loop. Exceptions queued for quick check; optional confirm before creating a brand-new contact. Acceptance test. Send a proposal email with a 3-line PDF quote to a non-existent-in-Act! recipient → contact created with suggested group, Note logs all 3 items + prices verbatim, follow-up Activity set; a corrupt PDF instead lands in the review queue. Depends on. Email platform confirmed; OCR/vision; convention agreed with sales; Act! Activities write access. Effort drivers. Attachment parsing variance; new-contact dedup against 10k base; group-suggestion logic; follow-up scheduling handoff.
SALES-010 — Email Exchange Summarising to the CRM
Medium · Est. 4–6 days
Goal. When a meaningful client email exchange closes, write a concise Act! Note capturing what was discussed, offered, agreed and at what rate — ignoring routine noise. Trigger. Thread-quiescence: inbox-watch on each rep’s mailbox detects no new message on a client thread for N hours (config). O365/Exchange (TBC). Inputs / sources. Full thread (all messages, both directions), participant addresses, rep identity. Systems & APIs. Email integration (TBC), LLM API, Act! Web API — Contacts, Companies, Notes, Groups; Teams digest. Build (n8n flow). 1) Inbox-watch captures new client mail; write thread + last-activity timestamp to a state store (n8n Data Table). 2) Schedule node sweeps for threads idle ≥N hours. 3) Noise filter: drop threads that are pure confirmations/pleasantries/auto-replies (rules + LLM classifier). 4) Assemble ordered thread text. 5) LLM summarises. 6) Match contact by external participant email. 7) POST Act! Note. 8) Tag budget/timing signals. 9) Append to rep digest. 10) Ambiguous match → review queue. AI / model work. Two-stage: (a) classifier → is_meaningful; (b) summariser → {summary, package_offered, rate_offered, agreed_or_promised[], budget_signal, timing_signal, contact_email, confidence}. Reads as clean history, not a transcript dump; rate captured explicitly and verbatim. Data model / writes. One Act! Note per closed exchange, stamped date · source=“Email exchange” · salesperson, package + rate as distinct lines so they’re checkable before re-quoting; budget/timing tagged for the follow-up engine. Edge cases & failure modes. Thread reopens after summarising → append supplementary Note, don’t duplicate. Internal-only/mixed thread → summarise external-facing content only. Low · Est. 2–3 days
Goal. Deliver a weekly written leadership brief from dashboard data, and fire early alerts when an open issue or event tracks materially behind its equivalent point last cycle. Trigger. Weekly schedule (brief); continuous/daily comparison sweep (alerts) — fires immediately when an issue/event falls behind its prior-cycle equivalent point. Inputs / sources. SALES-026 metrics store (revenue by title/issue, activity highlights, cycle comparisons); SALES-027 stall counts; exceptions/decisions needing attention. Systems & APIs. n8n (Schedule + comparison sweep); metrics store (read); LLM API (brief drafting); email/Teams delivery; summary archive store. Read-only over SALES-026/027 — no source writes. Build (n8n flow). 1) Weekly Schedule node pulls the week’s essentials from the metrics store: revenue position by title/issue, activity highlights, stalled sold items, exceptions needing a decision. 2) Model composes a short readable brief (not a spreadsheet) from the structured inputs, with evidence links per point. 3) Deliver brief to leadership (email/Teams). 4) Continuous comparison sweep evaluates each open issue/event against its prior-cycle equivalent point; when the gap exceeds threshold, generate an alert with the gap quantified + linked records. 5) Deliver alerts immediately via Teams/email. 6) Archive each brief to the summary store for cross-cycle trend review. AI / model work. Model drafts the narrative brief. Input: structured weekly metrics + deltas + stall list + exceptions. Force an issue behind its prior-cycle point → an alert fires promptly with the gap quantified and records linked; a second identical trigger within cooldown does not re-fire. Depends on. SALES-026 (metrics + cycle comparison), SALES-027 (stall data); LLM API; email/Teams delivery. Effort drivers. Reliable narrative generation with guaranteed sections; issue-relative comparison + false-alert suppression; alert dedupe/cooldown.
